In basic information retrieval, user queries are simple and localized: *"What is our travel reimbursement per diem?"* The retriever looks up one document chunk, passes it to the language model, and returns a direct answer.

In enterprise workflows, the most valuable questions are rarely single-hop. Business users ask complex, cross-cutting comparative questions:
- *"Compare the liability caps and termination clauses across our three largest cloud vendor contracts."*
- *"How do the safety guidelines in the revised 2026 manufacturing handbook differ from the 2024 edition?"*
- *"Synthesize the customer feedback across all five regional quarterly business reviews."*

Naive RAG pipelines fail completely on these queries. Vector search retrieves chunks biased toward one dominant document, ignoring the others and producing incomplete, skewed comparisons.

Building an AI knowledge assistant capable of multi-document synthesis requires an agentic query decomposition architecture. Here is how modern software teams implement it.

## Why Single-Hop Vector Retrieval Fails on Comparisons

Standard RAG architectures face three primary failure modes when answering comparative multi-document questions:

- **Vector Cosine Bias**: When you execute a single vector query for *"Compare Contract A and Contract B"*, the embedding algorithm projects the query into a single point. If Contract A has slightly more semantic overlap with the prompt keywords, all top-k retrieved chunks will originate from Contract A, leaving Contract B unrepresented in the context window.
- **Context Fragmentation**: Even if chunks from both documents are retrieved, they arrive as jumbled, out-of-order text fragments. The language model struggles to align parallel clauses accurately.
- **Lost-in-the-Middle Attention Degradation**: As multiple lengthy documents are dumped into a large prompt, language models suffer from positional bias, frequently ignoring information positioned in the middle of the context window.

## The Solution: Agentic Query Decomposition

Rather than executing a single, naive retrieval call, modern systems employ **Query Decomposition**:

1. **Query Planning Agent**: When a user prompt is identified as comparative, a lightweight planning LLM analyzes the request and breaks it into independent sub-queries:
   - Sub-query 1: *"Extract SLA terms and penalty clauses from Vendor A agreement."*
   - Sub-query 2: *"Extract SLA terms and penalty clauses from Vendor B agreement."*
2. **Targeted Parallel Retrieval**: Execute isolated vector searches for each sub-query, filtering by specific document metadata (`document_id: "vendor_a.pdf"` and `document_id: "vendor_b.pdf"`). This guarantees equal, unbiased representation for both entities.
3. **Structured Entity Extraction**: Before synthesis, extract key clauses into a normalized intermediate schema (e.g., JSON representation of SLA uptime, credit percentages, and notification windows).

```python
# Multi-document query decomposition pattern
def execute_comparative_rag(user_query: str):
    # Step 1: Decompose query into isolated document targets
    plan = query_planner.plan_comparison(user_query)
    # Example plan: [{"doc_id": "contract_a", "sub_query": "liability limits"}, ...]
    
    extracted_contexts = {}
    
    # Step 2: Parallel targeted retrieval per document
    for task in plan.tasks:
        chunks = vector_db.query(
            query=task.sub_query,
            filter={"document_id": {"$eq": task.doc_id}},
            top_k=3
        )
        extracted_contexts[task.doc_id] = "\n\n".join(c.text for c in chunks)
        
    # Step 3: Comparative synthesis with balanced context
    return synthesizer.generate_comparison(user_query, extracted_contexts)
```

## Map-Reduce and Iterative Refinement for Large Corpora

When a user asks to synthesize insights across ten or twenty documents (such as summarizing customer feedback across an entire enterprise department), dumping all chunks into a single context window is expensive and leads to dropped facts:

- **Map Step**: Process each document in parallel using a focused extraction prompt, generating a concise 200-word structured brief per document.
- **Reduce Step**: Aggregate the concise briefs into a final synthesis prompt, directing the model to identify patterns, recurring themes, and anomalies across the full set.

## Preventing Hallucinations in Comparative Summaries

Comparative analysis creates high risk for false equivalencies:
- **Explicit Schema Enforcement**: Instruct the synthesis model to output comparisons across explicit, standardized categories (e.g., Scope, Fees, Liability, Term).
- **Flagging Missing Data**: If Document A specifies an indemnification cap of $1,000,000 but Document B is silent on the topic, the assistant must explicitly declare that Document B contains no matching clause, rather than assuming terms are identical.

## Key Takeaway

Enterprise knowledge work is fundamentally comparative. By decomposing complex user prompts into isolated sub-queries, running targeted parallel retrievals, and synthesizing structured intermediate briefs, engineering teams deliver AI assistants capable of deep, multi-document analysis.
