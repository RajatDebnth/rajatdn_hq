# Production performance audit

Audit date: 2026-09-16. Scope: source boundaries, dependencies, assets, and a fresh Next.js 16.3.5 webpack production build. Figures below are local generated-file measurements, not network transfer timings or Lighthouse scores.

## Outcome

The site is intentionally lean and fully prerendered: public pages are static or generated at build time, the only application Client Component is the mobile navigation, and no analytics, third-party browser scripts, animation library, web fonts, or published raster images are present. The actual code fix was to make all three repository-controlled image paths responsive with `sizes` and replace deprecated Next.js 16 `priority` usage. No redesign or dependency addition was warranted.

JS figures sum referenced production script files once per page and gzip each file locally. They are **not** a measured first-visit transfer: deployed compression, browser caching, HTTP protocol, and already-cached shared chunks can change delivered bytes. The article adds about 5.3 KB gzipped JS over the sample base because its route has an additional chunk; most referenced JS is Next.js/React runtime and shared framework code. The mobile-navigation application chunk is small relative to that runtime. HTML includes Next.js' serialized React Server Component payload, which explains why the raw article document is comparatively large while compression remains effective.

## Findings by area

| Area | Finding | Decision |
| --- | --- | --- |
| JavaScript and hydration | One `"use client"` component, limited to the interactive mobile menu. Pages, cards, content, metadata, and site chrome are Server Components. | Keep the client boundary: menu expansion and closing after a client-side route change genuinely require state/event handling. Do not force full-page navigation merely to remove a small component. |
| Code splitting | Shared framework scripts dominate; route-specific page scripts are tiny on ordinary pages. The article has its own additional chunk. | No broad client import or eager chart/animation package to split further. Avoid a bundle-analyzer dependency without a concrete need. |
| Images | No real project/article raster image is published yet; the favicon is SVG and the Open Graph image is generated by the framework. Existing conditional content images use `next/image` with intrinsic dimensions. | Added `sizes` for project, article-hero, and MDX captioned images; removed deprecated `priority`, using `fetchPriority="high"` only for the optional article hero. Actual file-size/format optimization awaits real assets. |
| Fonts | System sans and monospace stacks; no `next/font`, remote font, `@font-face`, or font download. | Keep system fonts; adding a hosted font would create an extra asset and possible layout shift for no current product need. |
| CSS and motion | One 29.1 KB production stylesheet (6.4 KB local gzip). Motion is limited to color transitions and smooth scrolling; reduced-motion rules disable those effects. | No animation library or CSS rewrite. Reassess only if a real mobile paint issue is measured. |
| Third-party scripts | None. JSON-LD is an inline data script, not executable analytics or tracking. | Do not add analytics in this phase. |
| Dependencies | Runtime dependencies are Next.js, React, React DOM, `gray-matter` for frontmatter, and `next-mdx-remote` for repository MDX. Each has a current use. | No package removal/addition. `npm ls --depth=0` showed some extraneous packages in the local install, but they are not declared in `package.json`; a clean deployment install should be checked separately. |
| Repeated rendering | Blog/content parsing can recur during build across sitemap, metadata, and route generation, but pages are statically generated, so it is not a per-visitor cost. | Do not add caching abstractions for an unmeasured build-time issue. |
| Caching | The build outputs static/SSG pages, static metadata routes, and shared hashed assets, allowing Vercel/Next caching. No request-time data fetch or custom backend is present. | Let the framework/CDN manage immutable asset caching; verify live response headers after deployment before changing policy. |
| Mobile | Responsive layouts and compact CSS/assets are in place. The main mobile constraint is the shared Next.js/React JS baseline, not heavy portfolio visuals. | A real throttled-device Lighthouse/field measurement is still needed; local gzip estimates alone do not prove Core Web Vitals. |

Next.js 16 documents that `sizes` affects responsive `srcset` selection and that omitting it can cause unnecessarily large image downloads; it also marks `priority` deprecated in favor of clearer preload/fetch-priority behavior. See the repository's installed [`next/image` guide](node_modules/next/dist/docs/01-app/03-api-reference/02-components/image.md). The installed [Server/Client Components guide](node_modules/next/dist/docs/01-app/01-getting-started/05-server-and-client-components.md) confirms that Client Components should be limited to actual state, handlers, or browser APIs.

## Changes and validation

- `src/app/(site)/projects/[slug]/page.tsx`: responsive project-image `sizes`; removed `priority`.
- `src/app/(site)/blog/[slug]/page.tsx`: responsive article-hero `sizes`; replaced `priority` with `fetchPriority="high"`.
- `src/components/blog/mdx-components.tsx`: responsive captioned-image `sizes`.
- `npm run lint`: passed.
- `npm run typecheck`: passed.
- `npm run build`: passed; public pages remain static or SSG.
- Production payload sampled from generated HTML, CSS, and JS; no published page currently renders a raster content image, so image-byte savings cannot yet be quantified.

## Remaining performance risks

1. **Mobile field performance remains unmeasured.** Run Lighthouse with mobile throttling and, after launch, inspect real Core Web Vitals before claiming performance targets.
2. **Future images need an asset budget.** Before publishing, export appropriately sized WebP/AVIF/JPEG as relevant, verify intrinsic dimensions and alt text, and inspect the actual `srcset`/transfer on mobile. Do not use giant originals or auto-preload every image.
3. **Shared framework JS is the primary first-visit payload.** This is a Next.js runtime cost in the current architecture; route-level application JS is small. Reassess only after real mobile evidence rather than replacing framework navigation speculatively.
4. **Article HTML grows with content.** Long MDX pages include rendered article HTML plus the RSC payload. Monitor unusually long pages, code samples, and diagrams as the library expands.
5. **Live caching needs verification.** The local build cannot confirm Vercel response headers, CDN hit rate, image optimizer behavior, or social-image caching.
