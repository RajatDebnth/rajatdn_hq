In enterprise B2B SaaS, multi-tenant data leakage is an existential failure mode. If an enterprise customer discovers that their AI knowledge assistant returned an invoice, executive strategy memo, or employee review belonging to another customer, the outcome is swift: immediate contract cancellation, mandatory breach notifications under GDPR and CCPA, and devastating reputational damage.

In traditional SaaS web applications, relational databases isolate data through foreign keys, schema isolation, and database connection pools. 

However, RAG pipelines introduce new vectors of leakage:
- Semantic search across shared vector indexes where metadata filters are stripped by query preprocessors.
- Shared semantic caches that return cached LLM responses across different tenant sessions.
- Ingestion pipelines that mix up asynchronous document parsing tasks in shared queues.

To eliminate cross-tenant leakage, engineering teams must implement **Defense-in-Depth Retrieval Sanitization**—enforcing strict tenant boundaries across every layer of the ingestion, caching, retrieval, and generation lifecycle.

---

### The Anatomy of a Cross-Tenant Retrieval Breach

Consider an incident where Tenant A asks their support copilot: `"What are our contractual terms with Acme Corp?"`

```
[Insecure Shared Pipeline - Anatomy of a Leak]
1. Tenant A User sends query
       |
       v
2. Application Query Rewriter (Expands query via LLM)
       LLM rewrites query to: "Acme Corp contract renewal terms SLA"
       (Drops internal tenant context variables during prompt restructuring)
       |
       v
3. Vector Database Retrieval
       Executes semantic vector search WITHOUT hard tenant filter
       Retrieves top 5 chunks across the entire corporate index
       (Chunk 1 belongs to Tenant B's confidential Acme agreement!)
       |
       v
4. Generator Model (GPT-4o / Claude 3.5 Sonnet)
       Synthesizes response quoting Tenant B's proprietary pricing terms
       |
       v
5. Tenant A views Tenant B's confidential agreement in their UI
```

The failure was not caused by a flawed LLM; it occurred because the retrieval infrastructure lacked deterministic tenant boundary enforcement.

### 4 Architectural Safeguards to Stop Tenant Leaks

#### 1. Deterministic Pre-Retrieval Filter Injection

Never allow query rewriting models or client-side parameters to construct retrieval filters. Instead, inject the verified tenant identifier at the database driver layer right before execution:

```python
from typing import Dict, Any

class SecureVectorClient:
    def __init__(self, raw_vector_db):
        self._db = raw_vector_db

    def query(self, vector: list[float], tenant_id: str, client_filter: Dict[str, Any] = None, top_k: int = 5):
        if not tenant_id or not isinstance(tenant_id, str):
            raise ValueError("Security Violation: Missing or invalid tenant context")
        
        # Merge client filters into an immutable tenant-scoped compound filter
        secure_filter = {
            "$and": [
                {"tenant_id": {"$eq": tenant_id}}
            ]
        }
        
        # Safely append client-level filters (e.g., department, date range)
        if client_filter:
            secure_filter["$and"].append(client_filter)
            
        return self._db.query(
            vector=vector,
            filter=secure_filter,
            top_k=top_k,
            include_metadata=True
        )
```

By wrapping the raw vector database client inside a hardened proxy class, developers cannot physically execute an unfiltered query.

#### 2. Post-Retrieval Metadata Boundary Verification

Even with database-level filtering, defense-in-depth requires verifying retrieved documents before they reach the LLM context window. Implement an automated post-retrieval validator that checks every chunk:

```python
def validate_retrieved_chunks(retrieved_chunks: list[dict], expected_tenant_id: str) -> list[dict]:
    sanitized_chunks = []
    
    for chunk in retrieved_chunks:
        metadata = chunk.get("metadata", {})
        chunk_tenant = metadata.get("tenant_id")
        
        if chunk_tenant != expected_tenant_id:
            # Critical Security Alert: Database returned foreign tenant data!
            log_critical_security_incident(
                event="CROSS_TENANT_LEAK_PREVENTED",
                expected_tenant=expected_tenant_id,
                leaked_tenant=chunk_tenant,
                chunk_id=chunk.get("id")
            )
            # Instantly drop corrupted chunk
            continue
            
        sanitized_chunks.append(chunk)
        
    return sanitized_chunks
```

If a misconfigured database index or corrupted replica returns a chunk from another tenant, the post-retrieval assertion drops the chunk and alerts the InfoSec on-call engineer before the data ever touches the LLM context window.

#### 3. Tenant-Isolated Semantic Caching

Semantic caching reduces LLM latency and cost by serving cached responses for recurring user queries. However, a shared semantic cache is a notorious source of cross-tenant data leaks.

If Tenant A and Tenant B both ask: `"What is our monthly sales quota?"`, a naive semantic cache could return Tenant A's private sales target to Tenant B.

To prevent cache contamination, prefix all semantic cache keys with the tenant ID:

```python
import hashlib

def generate_cache_key(tenant_id: str, query_embedding: list[float]) -> str:
    # Hash query vector for deterministic namespace lookup
    vector_signature = hashlib.sha256(str(query_embedding).encode()).hexdigest()
    # Enforce hard namespace separation in Redis
    return f"cache:rag:{tenant_id}:{vector_signature}"
```

In vector semantic caches (such as Redis Stack or Qdrant), always include `{"tenant_id": tenant_id}` in the cache similarity lookup filter.

#### 4. Isolated Asynchronous Ingestion Queues

Cross-tenant leaks often occur before indexing, inside asynchronous document processing pipelines (Celery, BullMQ, or AWS SQS). If worker tasks share global temp directories or reuse uncleaned OCR scratch disks, documents can cross-contaminate.

- **Ephemeral Container Storage:** Process document OCR and PDF extraction in ephemeral scratch containers that terminate after each batch.
- **Tenant-Scoped Object Storage:** Store raw files in structured S3 bucket prefixes: `s3://company-rag-vault/tenants/{tenant_id}/documents/{doc_id}/`. Enforce IAM bucket policies preventing cross-prefix access.

### Security Audit Checklist for Engineering Teams

Before deploying shared-index RAG systems to production:
1. **Automated Cross-Tenant Penetration Tests:** Run automated CI test suites where synthetic Tenant X queries the RAG endpoint using known phrases from Tenant Y's documents, asserting 100% zero-retrieval success.
2. **Strict Ingestion Validation:** Ensure document ingestion pipelines validate that uploaded files belong to the authenticated session before parsing and embedding.
3. **Audit Trail Immutability:** Log all retrieval events with calling `tenant_id`, retrieved chunk IDs, and query timestamps to an append-only audit log for compliance verification.
